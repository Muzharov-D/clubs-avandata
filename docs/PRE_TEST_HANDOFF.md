# Pre-Test Handoff — Clubs · Avandata

Контекст для СВЕЖЕЙ сессии, которая одним заходом закроет финальный список правок
перед передачей платформы в тест. Цель этого дока — чтобы новая сессия НЕ
переоткрывала уже выясненное (дорого) и работала эффективно.

---

## 1. Доступ и проверка (ВАЖНО для скорости/стоимости)

- **Прод фронт** = `https://clubs-avandata.vercel.app` (Vercel). **Бэкенд** = Render.
  Кастомный домен `clubs.avandata.ru` из песочницы НЕ открывается (TLS падает).
- **Логин**: тренер `coach2010` / пароль `legirus 2010` — **пароль вводит пользователь**
  (правило безопасности: не вводим пароли). Сессия живёт (TTL токена поднят до 24ч).
- **Браузер**: Claude-in-Chrome (`mcp__Claude_in_Chrome__*`), подключён к Chrome юзера с
  прод-сессией. `tabs_context_mcp` → `navigate` → действия.
- ⚠️ **СТОИМОСТЬ — главный урок прошлой сессии (~$900!):** браузерные **скриншоты ОЧЕНЬ
  дорогие** и периодически сбоят (`clip.scale` binding error). ДЕШЁВЫЕ и надёжные
  альтернативы для проверки:
  - `get_page_text` — читать текст страницы (подписи, значения, склонения).
  - `javascript_tool` — **измерять геометрию/состояние** (`getBoundingClientRect`,
    `getComputedStyle`), фетчить API из контекста страницы (токен в
    `localStorage['avandata.auth.token']`, слать `Authorization: Bearer`).
  - Скриншот — ТОЛЬКО когда нужен реальный визуал и текст/измерение не отвечают.
- **Деплой**: push в `main` → Vercel редеплоит фронт ~1-2 мин (быстро), **Render
  редеплоит бэкенд медленнее (2-4 мин)**. Бэкенд-правки проверять с задержкой.
- Стиль работы можно «вслепую» (код+сборка+push, визуалку проверяет юзер) — это сильно
  дешевле; так и стоит делать для не-визуальных правок.

## 2. Источники истины (НЕ перепутать — на этом «горели»)

## 3. Данные/бэкенд-граблины (память-скиллы)

- **FORCE RLS**: `players` и tenant-таблицы под FORCE RLS. Сырой `pool.query` в скрипте
  отдаёт 0 строк — нужен `withTenant(slug, ...)` (ставит `app.tenant_id`).
- **`backend/.env` = ПРОД** (`DATABASE_URL` боевой Render-PG). **FFSPB_API_KEY есть** (40 симв).
- **Прод-запись требует ЯВНОГО подтверждения юзера** — авто-классификатор блокирует bulk-
  записи в прод без явного «да». Не обходить.
- **tsx ops-скрипты** (`backend/src/scripts/*.ts`) ИСКЛЮЧЕНЫ из прод-сборки
  (`tsconfig.build.json`). У них есть предсуществующие tsc-ошибки — это норма, прод-билд
  (`npm run build`) их не видит. Проверять бэкенд: `npm run build` (НЕ `tsc --noEmit`).
- Сборка: фронт `cd frontend && npm run build`; бэк `cd backend && npm run build`.

## 4. Ключевые общие утилиты (переиспользовать, не дублировать)

- `frontend/src/utils/num.js`:
  - `matchesWord(n)` — склонение «матч/матча/матчей».
  - `formLetterRu(result)` — W/D/L → В/Н/П (вся форма в UI кириллицей; латиница вычищена).
  - `plural`, `percentileRank`, `formatRaw`.
- `frontend/src/utils/players.js`:
  - `splitName(fullName)` → {first,last} с распознаванием обратного порядка «Фамилия Имя»
    по суффиксу (-ов/-ев/-ин/-ский/-ко…).
  - `surnameOf`, `shortNameFromPlayer`, `numberWithPos(number, position)` (без висячего «· »).
- `frontend/src/utils/pizzaTemplates.js`: `positionGroup(player)` — слова + лат/кириллич.
  коды → GK/DEF/MID/FWD. `POSITION_OPTIONS`, `TEMPLATES`, CIES-пиццы.
- `frontend/src/pages/ClubDashboard.tsx`: локальный `posGroup(code)` (по последней букве

- `frontend/src/components/analytics/PlayerDnaCard.jsx`: `playerArchetype(subject,
  seasonPlayers, basis)` — CIES-архетип (Финишёр/Атак.полузащитник/Дирижёр/…),

- Дистанция — везде км (хелперы делят на 1000); форма матча — `formLetterRu`; цвета —
  только CSS-токены (`var(--brand-*)`).

## 6. ИЗВЕСТНЫЕ ШЕРОХОВАТОСТИ / кандидаты в финальный список

**Мелкие баги, замеченные но не закрытые:**
- **«#1 Максим С.» в запасных НА СТРАНИЦЕ РАЗБОРА** (FormationField subs) всё ещё может
  показывать «Максим» — там игрок из match-данных, не из seasonRoster; проверить, что
  `shortNameFromPlayer` применяется к субам разбора (splitName уже чинит, но источник иной).
- **Count-up «0.00»** — рейтинг/значения мелькают нулём до анимации (page-text ловит 0.00).
  Намеренная анимация, но при глюке/медленной сети читается как баг. Можно стартовать
  анимацию ближе к цели или показывать «—» при 0.
- **Пропорция поля** доведена до 1.72 — если на узких экранах тесно, проверить мобайл
  (`@media max-width:768px`, aspect-ratio 2/3).
- Проверить, что после смены источника позиций все экраны (профиль/сравнение/нагрузка/
  пицца-шаблоны по позиции) берут НОВУЮ позицию консистентно.

## 7. Как вести «один большой заход» эффективно

1. Собрать ВСЕ правки в батчи по area (фронт-CSS / фронт-логика / бэкенд / данные).
2. Делать правки → `npm run build` (фронт+бэк) → 1 коммит на логический батч → push в main.
3. Проверять **дёшево**: `get_page_text` + `javascript_tool` (измерения/API), скриншот —
   точечно. НЕ гонять скриншот после каждой мелкой правки.
4. Бэкенд-правки — помнить про лаг Render; проверять с задержкой или через API-фетч.
5. Прод-записи (бэкфилл/уборка) — копить отдельно, делать с явным подтверждением юзера.
6. В конце — единый проход по ключевым экранам (логин→/club→/analytics→разбор→профиль→
   сравнение→тренировки→нагрузка→календарь) глазами юзера перед тестом.
