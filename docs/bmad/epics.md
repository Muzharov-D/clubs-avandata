# Дашборд федерации региона (Clubs · Avandata) — Разбивка на эпики

## Overview

Декомпозиция требований PRD, UX-спецификации и архитектуры в реализуемые истории. Эпики организованы по пользовательской ценности и фазам (F0 каркас → F1 MVP → Ф2 → Ф3). Каждая история независимо завершаема и не зависит от будущих историй своего эпика.

## Requirements Inventory

### Functional Requirements

- FR1: Федерация (`federation_admin`) входит в кабинет региона и видит только клубы своей федерации.
- FR2: Федерация работает в режиме только чтения и не изменяет данные клубов.
- FR3: Действия федерации фиксируются в аудите.
- FR4: Федерация видит сводные показатели региона (клубы, команды, игроки в реестре, разобранные матчи).
- FR5: Федерация видит честный охват — сколько клубов на базовом слое и сколько углубились (`paid`).
- FR6: Федерация видит динамику массовости и ленту активности региона.
- FR7: Федерация просматривает реестр всех клубов-членов с показателями и индикатором полноты данных.
- FR8: Федерация открывает профиль клуба (команды, тренеры, паспортизация, тариф).
- FR9: Федерация сравнивает клубы между собой по набору показателей.
- FR10: Федерация фильтрует и сортирует клубы по возрасту, тарифу, охвату.
- FR11: Федерация просматривает сводные турнирные таблицы по возрастам.
- FR12: Федерация видит результаты последнего тура и календарь по всем клубам турнира.
- FR13: Федерация просматривает кубковые сетки.
- FR14: Федерация видит охват и качество данных по каждому клубу.
- FR15: Федерация видит полноту паспортизации (дата рождения, фото, позиция, согласие) по клубам.
- FR16: Федерация видит статус согласий на обработку данных детей.
- FR17: Система не показывает федерации именные/детальные ПД ребёнка без `data_consent`.
- FR18: Федерация просматривает рейтинг игроков региона, нормированный против пула региона.
- FR19: Федерация открывает профиль игрока (перцентили, архетип CIES) — только при согласии.
- FR20: Федерация формирует «сборную региона» по позициям и возрастам.
- FR21: Федерация видит распределение игроков по кварталам рождения (RAE) обезличенно.
- FR22: Федерация видит продуктивность клубов (минуты молодых, прогрессия, переходы).
- FR23: Федерация экспортирует отчёты (CSV, печать PDF).
- FR24: Федерация сравнивает клубы по KPI в режиме бенчмаркинга.
- FR25: Администратор платформы создаёт федерацию и задаёт регион/родительский орган.
- FR26: Администратор платформы управляет членством клубов в федерации.
- FR27: Система авто-сидирует членство клубов по `dataProvider`/региону с ручной правкой.

### NonFunctional Requirements

- NFR1 (Изоляция): федерация не видит клубы вне своего региона — доказывается CI-тестом (гейт релиза).
- NFR2 (Согласие): именные ПД детей недоступны без `data_consent` — гейт релиза.
- NFR3 (Производительность): p95 кросс-тенантных агрегатов < 1.5 с.
- NFR4 (Доступность): WCAG AA на всех экранах.
- NFR5 (Аудит/Read-only): федерация только читает; действия логируются.

### Additional Requirements (из архитектуры)

- Единый шов фильтра членства `FED_MEMBERSHIP_SQL` в каждом федеративном SELECT.
- `withFederation()` (bypass + app-фильтр) в `tenantContext.ts`; RLS новых таблиц fail-closed.
- Слои данных = существующее `tenants.plan` (`free`/`paid`).
- Модуль `backend/src/federation` + `frontend/src/routes/federation` + schema-файлы; CI-гейт (tsc/build/schema-drift/rls-тест) + кейс изоляции федерации.
- Индексы: `federation_tenants(federation_slug, tier)`, `matches_tenant_season_idx`.

### UX Design Requirements

- UX-DR1: `CoverageStat` — двухслойная KPI-метрика честного охвата (как проп `coverage` у `StatTile`).
- UX-DR2: `RegionActivityFeed` — гетерогенная кросс-клубная лента.
- UX-DR3: `ClubRegistryTable` / `ClubRosterRow` — реестр клубов с логикой слоёв (full/listed) и сравнения.
- UX-DR4: `PassportCompletenessBars` — мульти-измерение полноты данных клуба.
- UX-DR5: Матрица состояний на каждом экране (загрузка/пусто/частичный охват/нет согласия/ошибка) + обезличенный режим.

### FR Coverage Map

- FR1, FR2, FR3 → Эпик 0 (доступ, read-only, аудит)
- FR25, FR26, FR27 → Эпик 0 (создание федерации, членство, авто-сид)
- FR4, FR5, FR6 → Эпик 1 (обзор региона)
- FR7, FR8, FR9, FR10 → Эпик 2 (клубы федерации)
- FR11, FR12, FR13 → Эпик 3 (соревнования региона)
- FR14, FR15, FR16, FR17 → Эпик 4 (целостность и согласия)
- FR18, FR19, FR20 → Эпик 5 (талант-пул и нормировка, Ф2)
- FR21, FR22 → Эпик 6 (возрастной эффект и развитие, Ф2–Ф3)
- FR23, FR24 → Эпик 7 (экспорт и бенчмаркинг, Ф3)

## Эпик 0: Безопасный доступ федерации к региону (F0)

Федерация получает безопасный, изолированный, read-only доступ к клубам своего региона. Фундамент, после которого все экраны F1 ложатся быстро.

### Story 0.1: Схема федераций и членства

As a администратор платформы,
I want таблицы `federations` и `federation_tenants`,
So that регион и состав его клубов можно описать в данных.

**Acceptance Criteria:**

**Given** пустую БД проекта
**When** применяется idempotent-миграция `00XX_federations.sql`
**Then** созданы `federations` (slug PK, name, region, parent_body, settings, brand) и `federation_tenants` (federation_slug, tenant_slug, tier `full`/`listed`, составной PK)
**And** повторный прогон миграции не падает (CREATE IF NOT EXISTS)
**And** Drizzle-схемы `federations.ts`/`federationTenants.ts` совпадают с БД (schema-drift зелёный).

### Story 0.2: Изоляция новых таблиц (RLS fail-closed)

As a разработчик платформы,
I want RLS-политику на `federations`/`federation_tenants`,
So that доступ к ним возможен только через контролируемый контекст.

**Acceptance Criteria:**

**Given** новые таблицы
**When** применяется `00XX_federation_rls.sql`
**Then** без контекста доступа SELECT возвращает 0 строк (fail-closed)
**And** bypass-контекст (admin/federation) читает корректно.

### Story 0.3: withFederation и единый шов фильтра членства

As a разработчик платформы,
I want хелпер `withFederation(slug, fn)` и фрагмент `FED_MEMBERSHIP_SQL`,
So that любой федеративный запрос изолирован одним переиспользуемым швом.

**Acceptance Criteria:**

**Given** `tenantContext.ts`
**When** вызывается `withFederation('ffspb', fn)`
**Then** в сессии выставлен bypass, а запросы фильтруются `tenant_id IN (SELECT tenant_slug FROM federation_tenants WHERE federation_slug=$1 AND tier='full')`
**And** `FED_MEMBERSHIP_SQL` экспортируется и используется как единственный источник фильтра
**And** хелпер предоставляет только read-путь (FR2).

### Story 0.4: Роль federation_admin и резолвинг контекста

As a федерация,
I want роль `federation_admin` с привязкой к моей федерации,
So that при входе я попадаю в кабинет своего региона, и мои действия логируются.

**Acceptance Criteria:**

**Given** пользователя с ролью `federation_admin` и `federationId`
**When** он логинится
**Then** JWT содержит claim `federationId`, `tenant_id = NULL`
**And** `/auth/me` отдаёт федеративный контекст
**And** действия федерации пишутся в аудит (FR3)
**And** CHECK-констрейнт роли в `users` обновлён миграцией.

### Story 0.5: Администратор создаёт федерацию и управляет членством

As a администратор платформы,
I want создавать федерацию и добавлять/убирать клубы из неё,
So that регион описан и им можно управлять.

**Acceptance Criteria:**

**Given** роль `platform_admin`
**When** POST создаёт федерацию (slug, region, parent_body) и PATCH меняет членство клуба
**Then** записи в `federations`/`federation_tenants` корректны (FR25, FR26)
**And** операции идут через `withBypassRLS` с `authorize('platform_admin')`.

### Story 0.6: Авто-сид федерации ФФСПб

As a администратор платформы,
I want скрипт сида, заводящий ФФСПб и членство всех её клубов,
So that реестр не пуст в день запуска.

**Acceptance Criteria:**

**Given** существующие клубы с `dataProvider='ffspb'`
**When** запускается `seedFederation.ts`
**Then** создана федерация `ffspb` и членство (`tier='full'`) для всех ffspb-клубов (FR27)
**And** повторный прогон идемпотентен.

### Story 0.7: Тест изоляции региона (гейт релиза)

As a разработчик платформы,
I want CI-тест, доказывающий, что федерация А не видит регион Б,
So that кросс-региональная утечка невозможна (NFR1).

**Acceptance Criteria:**

**Given** две федерации с разными клубами на непривилегированной роли
**When** федерация А запрашивает данные
**Then** клубы региона Б не возвращаются ни в одном эндпоинте
**And** запрос без `FED_MEMBERSHIP_SQL` ловится тестом «забытого фильтра»
**And** тест гоняется в CI до мержа.

### Story 0.8: Пустой кабинет федерации

As a федерация,
I want войти и увидеть навигацию кабинета,
So that я понимаю структуру продукта ещё до наполнения данными.

**Acceptance Criteria:**

**Given** вход `federation_admin`
**When** открывается кабинет
**Then** показан `SidebarNav` из 8 модулей, 3 активны (Обзор, Клубы, Соревнования), остальные — «Скоро» (не 404)
**And** шапка с брендом федерации; режим только чтения
**And** ProtectedRoute пускает только `federation_admin`.

## Эпик 1: Обзор региона (F1)

Федерация за взгляд видит пульс региона и честный охват.

### Story 1.1: Эндпоинт обзора с раздельными счётчиками слоёв

As a федерация,
I want сводные показатели региона с раздельным охватом,
So that я вижу масштаб и честную картину покрытия.

**Acceptance Criteria:**

**Given** `GET /api/v1/federation/overview`
**When** запрос выполняется в контексте федерации
**Then** возвращены счётчики (клубы, команды, игроки реестра, матчи) и **раздельно** `{ total, onPlatform(paid), listed }` (FR4, FR5)
**And** счётчики слоёв НЕ суммируются в один (контракт честного охвата)
**And** запрос использует `FED_MEMBERSHIP_SQL`.

### Story 1.2: Экран обзора с KPI и честным охватом (CoverageStat)

As a федерация,
I want ряд KPI с явным охватом,
So that «12 клубов · 5 на глубине» читается сразу.

**Acceptance Criteria:**

**Given** данные обзора
**When** открыт «Обзор региона»
**Then** показаны `StatTile` KPI + `CoverageStat` (проп `coverage`) с подписью слоёв (UX-DR1, FR5)
**And** числа `tabular-nums`, цвета через токены, WCAG AA (NFR4)
**And** состояния загрузки/пусто/ошибки по матрице (UX-DR5).

### Story 1.3: Динамика массовости и лента активности

As a федерация,
I want тренд массовости и ленту событий региона,
So that я вижу движение, а не только срез.

**Acceptance Criteria:**

**Given** обзор
**When** экран отрисован
**Then** показан `Sparkline` массовости и `RegionActivityFeed` (разбор загружен / тур сыгран / клуб добавлен) (FR6, UX-DR2)
**And** при отсутствии данных блок не показывается (деградация).

## Эпик 2: Клубы федерации (F1)

Федерация изучает, сравнивает и фильтрует клубы.

### Story 2.1: Реестр клубов

As a федерация,
I want таблицу всех клубов-членов с ключевыми показателями и охватом,
So that я вижу «кто есть кто» за один экран.

**Acceptance Criteria:**

**Given** `GET /federation/clubs` в контексте федерации
**When** открыт экран «Клубы»
**Then** `ClubRegistryTable` показывает клубы (команды, игроки, заливка-охват, рейтинг) (FR7, UX-DR3)
**And** listed-клубы приглушены, глубокие метрики «—»
**And** sticky-заголовок, заливка-скан, дубль цвета числом.

### Story 2.2: Профиль клуба

As a федерация,
I want открыть профиль клуба,
So that я вижу его команды, тренеров, паспортизацию и тариф.

**Acceptance Criteria:**

**Given** клик по строке реестра
**When** открыт профиль
**Then** показаны команды/возрасты, тренеры, тариф (`tenants.plan`) и `PassportCompletenessBars` (FR8, UX-DR4)
**And** контекст реестра сохраняется (боковая панель, focus-trap).

### Story 2.3: Сравнение клубов

As a федерация,
I want сравнить два клуба бок о бок,
So that решения опираются на сопоставление.

**Acceptance Criteria:**

**Given** выбор двух клубов
**When** запущено сравнение
**Then** показаны `StatCompareBar`/`DonutComparisonCard` по набору показателей (FR9)
**And** сравниваются только сопоставимые (одинаковая нормировка).

### Story 2.4: Фильтры и сортировка реестра

As a федерация,
I want фильтровать клубы по возрасту/тарифу/охвату,
So that я быстро нахожу нужные.

**Acceptance Criteria:**

**Given** реестр
**When** применён фильтр/сортировка
**Then** список обновляется мгновенно, без перезагрузки (FR10)
**And** активные фильтры видны и сбрасываемы.

## Эпик 3: Соревнования региона (F1)

Открытый слой — все клубы турнира, включая не на платформе.

### Story 3.1: Сводные турнирные таблицы по возрастам

As a федерация,
I want сводные таблицы по выбранному возрасту,
So that я вижу турнирную картину региона.

**Acceptance Criteria:**

**Given** `GET /federation/competitions` и `standings`
**When** выбран возраст
**Then** показана таблица из `standings.table_data`, наши клубы подсвечены брендом (FR11)
**And** отображаются и клубы не на платформе (имена из данных таблицы).

### Story 3.2: Результаты тура и календарь

As a федерация,
I want результаты последнего тура и предстоящий календарь,
So that я слежу за ходом соревнований.

**Acceptance Criteria:**

**Given** `calendar`/`matches`
**When** открыт раздел
**Then** показаны результаты тура (`LeagueMatchPreview`) и календарь с фильтром по клубу/возрасту (FR12).

### Story 3.3: Кубковые сетки

As a федерация,
I want видеть кубковые сетки,
So that картина соревнований полна.

**Acceptance Criteria:**

**Given** `cup_brackets`
**When** открыт кубок
**Then** показана сетка `CupBracket` по раундам (FR13)
**And** при отсутствии кубка раздел деградирует.

## Эпик 4: Целостность данных и согласия (F1, compliance)

Контроль данных + защита ПД детей. Содержит гейт релиза по согласию.

### Story 4.1: Охват и качество данных по клубам

As a федерация,
I want видеть охват и качество данных по каждому клубу,
So that я доверяю остальным цифрам.

**Acceptance Criteria:**

**Given** `data_quality` по матчам клубов
**When** открыт экран целостности
**Then** показан % разобранных матчей, средний `data_quality`, источники, пробелы (FR14)
**And** заливка-скан с дублем числом.

### Story 4.2: Полнота паспортизации

As a федерация,
I want видеть полноту паспортизации по клубам,
So that я понимаю, где реестр неполон.

**Acceptance Criteria:**

**Given** `players` (birthDate, photoUrl, position, dataConsent)
**When** открыт экран
**Then** показан % полей по клубам через `PassportCompletenessBars` (FR15).

### Story 4.3: Статус согласий

As a федерация,
I want видеть статус согласий на обработку данных детей,
So that я инициирую сбор до того, как это станет проблемой.

**Acceptance Criteria:**

**Given** `players.data_consent`
**When** открыт экран
**Then** показана сводка согласий по клубам, выделены проседающие (FR16).

### Story 4.4: Гейт согласия (release gate)

As a федерация,
I want гарантию, что без согласия именные ПД ребёнка мне недоступны,
So that мы соответствуем 152-ФЗ.

**Acceptance Criteria:**

**Given** игрока без `data_consent=true`
**When** федерация запрашивает любые данные
**Then** именные/детальные ПД не возвращаются; игрок участвует только в обезличенных агрегатах (FR17, NFR2)
**And** проверка централизована в `aggregations` (один шов)
**And** покрыта тестом-гейтом релиза.

## Эпик 5: Талант-пул и нормировка (Фаза 2)

### Story 5.1: Уникализация игрока между клубами

As a федерация,
I want, чтобы игрок, игравший за два клуба, считался один раз,
So that региональный рейтинг честен.

**Acceptance Criteria:**

**Given** `players.externalIds`
**When** строится региональный пул
**Then** дубли уникализированы по person-id (`ext-{provider}-{nativeId}`)
**And** счётчик «игроков региона» не завышен дублями.

### Story 5.2: Рейтинг игроков, нормированный против пула региона

As a федерация,
I want рейтинг игроков, нормированный по позиционному пулу региона,
So that таланты сопоставимы между клубами.

**Acceptance Criteria:**

**Given** `match_players` и позиции
**When** открыт талант-пул с фильтрами (возраст/позиция/мин. минуты)
**Then** показан рейтинг, перцентиль против пула региона (FR18)
**And** имена только при согласии, иначе обезличенный вклад.

### Story 5.3: Профиль игрока (с гейтом согласия)

As a федерация,
I want профиль игрока с перцентилями и архетипом,
So that я оцениваю талант предметно.

**Acceptance Criteria:**

**Given** игрока с `data_consent=true`
**When** открыт профиль
**Then** показаны `PizzaChart`/`PlayerRadar` и архетип CIES (FR19)
**And** без согласия — силуэт «Игрок №…», без имени/фото.

### Story 5.4: Сборная региона по позициям

As a федерация,
I want автоподбор лучших по позициям/возрастам,
So that отбор в сборную опирается на данные.

**Acceptance Criteria:**

**Given** региональный рейтинг
**When** открыт автоподбор сборной
**Then** показан состав «сборной региона» на `FormationField` (лучший на позицию/возраст) (FR20).

## Эпик 6: Возрастной эффект и развитие (Фаза 2–3)

### Story 6.1: Распределение по кварталам рождения (RAE)

As a федерация,
I want распределение игроков по кварталам рождения,
So that я вижу смещение отбора по зрелости.

**Acceptance Criteria:**

**Given** `players.birthDate`
**When** открыт экран возрастного эффекта
**Then** показано распределение Q1–Q4 по региону/клубу/возрасту, обезличенно, с эталоном 25% (FR21)
**And** выделены клубы с перекосом.

### Story 6.2: Продуктивность клубов

As a федерация,
I want метрики продуктивности клубов,
So that я оцениваю развитие, а не только результат.

**Acceptance Criteria:**

**Given** минуты/возраст/история переходов
**When** открыт экран развития
**Then** показаны минуты молодых, прогрессия, переходы между клубами (FR22)
**And** при недостатке истории сезонов блок честно помечает неполноту.
