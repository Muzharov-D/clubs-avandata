# Product Requirements Document — Дашборд федерации региона (Clubs · Avandata)

**Author:** Дмитрий
**Date:** 2026-06-14

---

## Краткое резюме

«Дашборд федерации региона» — кабинет региональной федерации (ФФСПб) поверх мульти-тенантной платформы Clubs · Avandata, дающий регулятору единую сопоставимую картину детско-юношеского футбола региона. Клубы изолированы как тенанты, и федерация — хотя сама порождает данные соревнований (ffspb) — не имеет кросс-клубного среза: решения о допуске, контроле честности, распределении ресурсов и отборе в сборную принимаются по разрозненным отчётам и связям, а не по данным. Пользователь — роль `federation_admin` (read-only): руководитель федерации, спортивный директор, методист, администратор. Продукт по сути — **инструмент поддержки решений регулятора**, а не аналитическая витрина.

### Что делает продукт особенным

Федерация впервые видит каждый клуб и каждого игрока **против пула всего региона** — сопоставление, недоступное ни одному клубу в одиночку. В отличие от типовых федеративных систем (реестр: кто зарегистрирован), платформа уже несёт редкую **per-player аналитику** (SportVisor: рейтинги, действия, карты) — «сколько детей играет» превращается в «как и насколько хорошо». Ключевой инсайт: данные соревнования порождает сама федерация, поэтому базовый слой по всем клубам — её право по **обязанности членства**, а не предмет согласия клуба. Глубина — премиум (`paid`), который клуб докупает; именные данные ребёнка дополнительно гейтятся согласием родителя (152-ФЗ). Федерация финансирует базовый план (`free`) всем клубам-членам — маппится на существующее `tenants.plan`.

## Контекст и классификация

**Тип:** SaaS B2B (мульти-тенантный дашборд), вторично web-app.
**Домен:** спорт / детско-юношеский футбол — управление федерации. Профиль соответствия: edtech (данные несовершеннолетних) + govtech (регулятор, прозрачность, доступность WCAG AA) + 152-ФЗ (обработка персональных данных детей).
**Сложность:** ВЫСОКАЯ — цена ошибки кросс-тенантной изоляции × персональные данные детей × ответственность за корректность решений регулятора.
**Контекст:** brownfield — надстройка над живой кодовой базой и данными.

### Переформулировка (First Principles)

Продукт — не «аналитический дашборд», а **инструмент поддержки решений регулятора**: каждый экран ведёт к действию федерации (допуск к соревнованиям, контроль честности, распределение ресурсов, отбор в сборную региона), а не к голой цифре.

Фундаментальные истины, на которых стоит продукт:
- Федерация **порождает** данные соревнования (турнир / ffspb) → «открытый слой» и обязанность клуба делиться базой — её право, а не натяжка.
- Решения требуют **единого мерила** → региональная нормировка показателей (перцентиль против пула региона, а не клуба) — базовый принцип, не опция.
- Ценность = **снижение неопределённости перед решением** → метрика успеха меряет уверенность/скорость решения, а не «охват данными».
- read-only для MVP, но **архитектурно заложить шов под будущие действия** федерации.

### Бизнес-модель

- Федерация финансирует **базовый план (`free`)** для всех клубов-членов → базовые показатели по всем, по **обязанности членства** (не opt-in).
- Клуб сам доплачивает за **глубину (`paid`)** — расширенные показатели. Маппится на существующее поле `tenants.plan` (`free` / `paid`).
- Юридическая граница: обязанность клуба делиться ≠ согласие родителя. Именные данные ребёнка в глубоком слое — только через `data_consent` (152-ФЗ).

### Масштаб

Мульти-федерация (иерархия РФС → МРО → регион) — **потенциально**. Модель тенантов проектируем так, чтобы не предполагать единственную федерацию, но иерархию в MVP не строим (шов, не бетон).

## Критерии успеха

### Успех пользователя

- Руководитель получает **единую сопоставимую картину** для решения и отчёта в РФС/МРО без ручного сбора по клубам.
- Спорт-директор/методист отвечает на «как дела у клуба X / возраста Y» за **≤ 30 секунд, ≤ 3 клика**.
- Aha-момент: впервые видит клуб и игрока **против пула всего региона**.
- Эмоция: уверенность («решаю по данным, не по слухам»), без перегруза.

### Бизнес-успех

- **3 месяца:** ФФСПб подключена; все клубы-члены заведены на базовый план; дашборд показывает реальные данные по всем (не пусто).
- **12 месяцев:** конверсия `free → paid` (клуб докупает глубину) — ключевая метрика; целевой ориентир 15–20% клубов за сезон (подтвердить). Федерация продлевает финансирование (ретеншн федерации).
- Метрика «это работает»: федерация принимает **≥ 1 решение в месяц со ссылкой на дашборд** (допуск/проверка/отбор/ресурс).

### Технический успех

- **Кросс-тенантная изоляция доказана тестом** (федерация А не видит клуб региона Б) — гейт релиза.
- **Гейт согласия:** именные данные ребёнка недоступны без `data_consent` — доказывается тестом.
- p95 кросс-тенантных агрегатов **< 1.5 с** (ориентир) на текущем объёме данных.
- CI-гейт проекта зелёный: `tsc` + build + проверка дрейфа схемы + RLS-тест изоляции.

### Измеримые результаты

- Время до ответа «как дела у клуба X» ≤ 30 секунд.
- **100% клубов-членов** на базовом слое к запуску.
- 0 инцидентов кросс-региональной утечки данных.
- Региональная нормировка работает: любой ключевой показатель сравним между клубами.
- Конверсия `free → paid` (бизнес-метрика).

## Пользовательские сценарии

### Сценарий 1 — Руководитель федерации (Сергей): отчёт и допуск (MVP)

Сергей готовит отчёт в МРО и параллельно решает, допускать ли клуб с тонким составом к старшему турниру. Сегодня он обзванивает клубы и сводит разрозненные таблицы вручную — это два дня. Он открывает «Обзор региона»: 12 клубов, все на базовом слое, охват данными виден честно. Переходит в реестр, видит клуб с провисающей глубиной состава по нужному возрасту. **Кульминация:** решение о допуске обосновано данными за минуты, а не ощущением. **Итог:** отчёт выгружен, решение задокументировано со ссылкой на дашборд.
→ Возможности: обзорные KPI, честный охват, реестр клубов, профиль клуба, экспорт.

### Сценарий 2 — Спортивный директор (Андрей): отбор в сборную региона (Фаза 2)

Андрей собирает сборную региона U14. Раньше он опирался на советы знакомых тренеров — субъективно и узко. Он открывает талант-пул региона, фильтрует по позиции и минимуму минут; рейтинг нормирован против пула всего региона, а не одной команды. Видит игрока из небогатого клуба, которого иначе бы не заметил. **Кульминация:** именной профиль доступен — у клуба `paid` и есть согласие родителя; для остальных вклад в распределение обезличен. **Итог:** состав собран по данным, с честной географией талантов.
→ Возможности: талант-пул, региональная нормировка, гейт согласия, «сборная региона».

### Сценарий 3 — Методист (Елена): качество и возрастной эффект (Фаза 2–3)

Елена отвечает за методику. Её гложет подозрение, что клубы отбирают «по физике» — детей начала года. Она открывает экран относительного возрастного эффекта: распределение по кварталам рождения по региону и по клубам. **Кульминация:** видит клуб с резким перекосом к Q1 — повод для методической работы, а не догадка. **Итог:** разговор с клубом подкреплён цифрой; продуктивность клубов становится измеримой.
→ Возможности: возрастной эффект (RAE), продуктивность клубов, бенчмаркинг.

### Сценарий 4 — Администратор ФФСПб (Ольга): реестр и согласия (MVP)

Ольга ведёт операционку федерации. Новый клуб вступил в федерацию — его нужно завести и убедиться, что данные потекли. Она проверяет членство клубов, видит охват и полноту паспортизации, замечает клуб с проседающими согласиями на обработку данных детей. **Кульминация:** точечно видит, где не хватает согласий, и инициирует их сбор — до того, как это станет проблемой 152-ФЗ. **Итог:** реестр полон, согласия под контролем, глубокий слой юридически чист.
→ Возможности: управление членством, целостность данных, статус согласий, паспортизация.

### Сводка возможностей из сценариев

Сценарии вскрывают пять групп возможностей: **обзор и реестр** (Сергей), **талант и нормировка** (Андрей), **качество, RAE, продуктивность** (Елена), **членство, согласия, целостность** (Ольга), и сквозную **приватность с гейтом согласия** во всех четырёх.

## Доменные требования

Домен высокой сложности (дети + регулятор) — раздел обязателен.

### Соответствие и регуляторика

- **152-ФЗ:** обработка персональных данных несовершеннолетних. Именные/детальные данные ребёнка доступны федерации только при согласии родителя (`players.data_consent`). Обязанность клуба делиться базой ≠ согласие родителя — два независимых основания.
- **Обязанность членства:** передача базовых обезличенных показателей федерации — следствие членства в федерации, фиксируется уставно/договорно, не запрашивается как opt-in.
- **Прозрачность регулятора (govtech-грань):** федерация видит сопоставимую картину по всем; «честный охват» показывается явно, без сокрытия неполноты.

### Технические ограничения

- **Изоляция региона:** федерация видит только клубы своей федерации; кросс-региональная видимость невозможна.
- **Гейт согласия:** обезличенные агрегаты — всегда; именной профиль ребёнка — только при `data_consent`.
- **Аудит:** действия федерации (просмотры, экспорт) логируются.
- **Только чтение:** федерация не изменяет данные клубов.

### Интеграции

- **ffspb** (`stat.ffspb.org`) — матчи, таблицы, календарь по всем клубам турнира (открытый слой), уже подключено.
- **SportVisor** — PDF/Excel-разборы матчей → per-player аналитика (глубокий слой), уже в платформе.
- **Существующая платформа Clubs · Avandata** — `tenants`/`teams`/`players`/`matches`/`match_players`/`standings`/`calendar`; поле `tenants.plan` (`free`/`paid`) как граница слоёв.

### Снижение рисков

- **Утечка через забытый фильтр членства** → единый шов фильтрации (`withFederation` / `FED_MEMBERSHIP_SQL`) + обязательный CI-тест изоляции.
- **Дедуп игрока между клубами** → в MVP «игроки» = записи реестра; уникализация по `externalIds` — предпосылка талант-пула (Фаза 2).
- **Неполнота данных** → деградация (блок не показываем без данных), честный охват вместо мусора.

## Инновации и новые паттерны

### Зоны инновации

- **Региональная нормировка для регулятора:** клуб и ребёнок против пула всего региона — то, что недоступно ни одному клубу в одиночку.
- **Per-player аналитика на уровне федерации:** федерации обычно ведут реестр («кто зарегистрирован»); здесь — «как и насколько хорошо играют», на базе SportVisor.
- **Открытый слой по обязанности членства:** снимает классический затык «клуб не делится с регулятором», превращая охват из риска принятия в данность.

### Рыночный контекст

Изучены 6 эталонных систем (FIFA Connect/COMET, DFBnet, FA Whole Game System, РФС Цифровая платформа, UEFA GROW, EPPP) + талант-наука (CIES, относительный возрастной эффект). Вывод: эти системы — преимущественно **реестры/перепись** и операционка соревнований; **per-player аналитика и региональная нормировка на уровне федерации — редкость**, особенно в российском детско-юношеском контуре. Подробности — `docs/FEDERATION_DASHBOARD_PLAN.md`, Часть I.

### Подход к валидации

- Пилот на одной федерации (ФФСПб) на уже имеющихся данных.
- Метрика инновации = принятые решения со ссылкой на дашборд (talent, допуск, методика).
- RAE-экран как дешёвая высокоценная проверка гипотезы «данные уже лежат, ценность извлекается тривиально».

### Снижение рисков инновации

- Если глубокий слой узок на старте — открытый слой самостоятелен и полезен (не зависит от согласий).
- Если нормировка спорна методически — показываем и абсолют, и перцентиль; методику фиксируем явно (наследуем CIES-референс).

## Требования к типу продукта (SaaS B2B)

### Обзор типа

Мульти-тенантная B2B-платформа с новым уровнем доступа (федерация) над существующими тенантами (клубами). Ключевые разделы типа: модель тенантов, матрица ролей, тарифы, интеграции, соответствие.

### Модель тенантов

- Клуб = тенант (существует). Федерация = **группа тенантов** через членство `federation_tenants` (federation_slug ↔ tenant_slug, tier).
- Новая сущность `federations` (slug, name, region, parent_body, settings). Спроектирована так, чтобы поддержать несколько федераций и иерархию РФС → МРО → регион (шов), без её реализации в MVP.
- Граница слоёв данных = существующее `tenants.plan`: `free` (база, финансирует федерация) / `paid` (глубина, оплачивает клуб).

### Матрица ролей и доступа

- `platform_admin` — владелец платформы; создаёт федерации, управляет членством; единственный, кто пишет в эти сущности.
- `federation_admin` (новая) — **read-only, region-scoped**; видит клубы своей федерации; не пишет данные клубов, не управляет платформой.
- `head_coach` / `team_coach` / `player` / `parent` — без изменений, scoped в клуб.
- Что видит федерация: базовый слой по всем клубам-членам; глубокий — по клубам `paid`; именные данные детей — только при `data_consent`.

### Тарифные планы

- `free` — базовые показатели; финансируется федерацией для всех клубов-членов; передаётся федерации по обязанности.
- `paid` — расширенная глубина (per-player аналитика); оплачивается клубом; для именных данных детей — гейт согласия.

### Список интеграций

ffspb (открытый слой), SportVisor (глубокий слой), существующий конвейер загрузки разборов, существующий CI-гейт (tsc/build/schema-drift/RLS-тест).

### Требования соответствия

152-ФЗ (согласие на ПД детей), обязанность членства (база), аудит действий федерации, доступность WCAG AA.

### Соображения реализации

Новый модуль `backend/src/federation` (+ `frontend/src/routes/federation`) и schema-файлы `federations`/`federationTenants` — по конвенции проекта «фича = модуль». Изоляция региона — единым швом фильтра членства; на managed-PG, где owner-роль обходит RLS, изоляция держится на app-фильтре, RLS — defense-in-depth. Детали — `docs/FEDERATION_DASHBOARD_TECH.md`.

## Границы и поэтапная разработка

### Стратегия MVP

MVP-философия — **problem-solving MVP**: дать регулятору сопоставимую картину по всем клубам на уже имеющихся данных, доказать ценность решений до инвестиций в глубокую аналитику. Минимум, после которого продукт полезен: федерация входит и за минуты отвечает на «что в регионе» и «как дела у клуба X».

### Состав MVP (Фаза 1)

- Каркас доступа: `federations` + `federation_tenants` + `withFederation()` + роль `federation_admin` + сид ФФСПб + тест изоляции.
- Три экрана на базовом слое по всем клубам: **Обзор региона**, **Клубы федерации**, **Соревнования региона**.
- Гейты релиза: изоляция региона и гейт согласия для именных данных.
- read-only; экспорт минимальный.

### После MVP (Фаза 2 — Growth)

Талант-пул региона с региональной нормировкой (глубокий слой, гейт согласия); относительный возрастной эффект (RAE); уникализация игрока (`externalIds`).

### Расширение (Фаза 3 — Vision)

Продуктивность клубов; бенчмаркинг и отчёты (CSV/PDF); витрина апгрейда `free → paid`; шов под действия федерации (допуск/санкции/отбор); мульти-федерация (РФС → МРО → регион); сводки в РФС.

### Снижение рисков (по типам)

- **Технические:** изоляция кросс-тенантных запросов — самый рискованный аспект; снимается единым швом + CI-тестом; нагрузка агрегатов — на лету сейчас, снапшоты при росте.
- **Рыночные:** риск принятия снят обязанностью членства (база); ценность доказывается решениями со ссылкой на дашборд.
- **Ресурсные:** MVP опирается на уже имеющиеся данные и поля (`tenants.plan`, `data_consent`); минимальная команда — текущая; запуск возможен на трёх экранах без глубокой аналитики.

## Функциональные требования

Контракт возможностей. Метка фазы указывает MVP / Фаза 2 / Фаза 3.

### Доступ и контекст федерации

- FR1: Федерация (`federation_admin`) входит в кабинет региона и видит только клубы своей федерации. (MVP)
- FR2: Федерация работает в режиме только чтения и не изменяет данные клубов. (MVP)
- FR3: Действия федерации (просмотр, экспорт) фиксируются в аудите. (MVP)

### Обзор региона

- FR4: Федерация видит сводные показатели региона (клубы, команды, игроки в реестре, разобранные матчи). (MVP)
- FR5: Федерация видит честный охват — сколько клубов на базовом слое и сколько углубились (`paid`). (MVP)
- FR6: Федерация видит динамику массовости и ленту активности региона. (MVP)

### Реестр и профиль клубов

- FR7: Федерация просматривает реестр всех клубов-членов с ключевыми показателями и индикатором полноты данных. (MVP)
- FR8: Федерация открывает профиль клуба (команды, тренеры, паспортизация, тариф). (MVP)
- FR9: Федерация сравнивает клубы между собой по набору показателей. (MVP)
- FR10: Федерация фильтрует и сортирует клубы по возрасту, тарифу, охвату данными. (MVP)

### Соревнования региона

- FR11: Федерация просматривает сводные турнирные таблицы по возрастам. (MVP)
- FR12: Федерация видит результаты последнего тура и календарь по всем клубам турнира, включая клубы не на платформе. (MVP)
- FR13: Федерация просматривает кубковые сетки. (MVP)

### Целостность данных и согласия

- FR14: Федерация видит охват и качество данных по каждому клубу. (MVP)
- FR15: Федерация видит полноту паспортизации (дата рождения, фото, позиция, согласие) по клубам. (MVP)
- FR16: Федерация видит статус согласий на обработку данных детей. (MVP)
- FR17: Система не показывает федерации именные или детальные персональные данные ребёнка без `data_consent`. (MVP — гейт)

### Талант-пул и нормировка

- FR18: Федерация просматривает рейтинг игроков региона, нормированный против позиционного пула региона. (Фаза 2)
- FR19: Федерация открывает профиль игрока (перцентили, архетип CIES) — только при согласии. (Фаза 2)
- FR20: Федерация формирует «сборную региона» по позициям и возрастам. (Фаза 2)

### Возрастной эффект и развитие

- FR21: Федерация видит распределение игроков по кварталам рождения (RAE) по региону, клубу и возрасту, обезличенно. (Фаза 2)
- FR22: Федерация видит продуктивность клубов (минуты молодых, прогрессия, переходы между клубами). (Фаза 3)

### Экспорт и бенчмаркинг

- FR23: Федерация экспортирует отчёты (CSV, печать PDF): сводка региона, паспортизация, качество данных. (MVP — базовый; Фаза 3 — расширенный)
- FR24: Федерация сравнивает клубы по набору KPI в режиме бенчмаркинга. (Фаза 3)

### Администрирование федерации

- FR25: Администратор платформы создаёт федерацию и задаёт регион/родительский орган. (MVP)
- FR26: Администратор платформы управляет членством клубов в федерации. (MVP)
- FR27: Система авто-сидирует членство клубов по `dataProvider`/региону с возможностью ручной правки. (MVP)

## Нефункциональные требования

### Производительность

- p95 кросс-тенантных агрегатов < 1.5 с на текущем объёме; при росте — материализованные снапшоты (ночной пересчёт через cron).

### Безопасность и приватность

- Кросс-тенантная изоляция региона на уровне запроса (единый шов членства) + RLS как defense-in-depth; доказывается CI-тестом.
- Гейт согласия для именных данных детей (`data_consent`); обезличенные агрегаты — всегда.
- Аудит действий федерации; режим только чтения для роли федерации.
- Соответствие 152-ФЗ.

### Масштабируемость

- Модель тенантов не предполагает единственную федерацию (шов под РФС → МРО → регион); иерархия не строится в MVP.
- Агрегаты переживают рост за счёт снапшотов, не переписывания.

### Доступность

- WCAG AA (контракт проекта): контраст, focus-visible, prefers-reduced-motion, tabular-nums на числах, дублирование цвета символом/числом (дальтоник-френдли).
- Тёмная тема (продуктовый регистр), русский интерфейс без англицизмов.

### Интеграция

- Надёжность ffspb-синка (открытый слой) с деградацией при сбое источника; существующий конвейер SportVisor (глубокий слой).
- Зелёный CI-гейт проекта (tsc, build, schema-drift, RLS-тест) как условие мержа.

### Надёжность

- Федерация — только чтение; ошибка в кабинете федерации не может повредить данные клубов.
- Деградация: блок не отображается при отсутствии данных, вместо пустого/мусорного состояния.

## Открытые вопросы

- Целевая конверсия `free → paid` и горизонт — подтвердить.
- Целевой p95 агрегатов — подтвердить на реальном объёме.
- Кто триггерит сбор согласий при проседании (федерация уведомляет клуб?) — процесс.
- Порядок реализации Фазы 2 (талант-пул vs RAE первым).
